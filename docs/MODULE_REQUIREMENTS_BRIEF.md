# Module Cleaner — Requirements Brief (charter)

Copied at seed time from the host repo's `handovers/MODULE_GENERATOR_AND_CLEANER_CANONICAL_OUTLINE_BRIEF_FOR_CODEX.md` (§6). Once this repo is live, **this file is the living spec**; the host brief's copy is historical.

## Mission

Remove addon modules from the system **completely and safely** — no orphan DB tables, no orphan files, no orphan settings/permissions/navigation — and detect + retire residue that earlier removals left behind. The host's own `uninstallModule()` deletes the module directory but deliberately retains owned tables, settings values, permission rows, and package records; the Cleaner is the tool that closes that gap, with backups, quarantine, dependency checks, typed confirmations, and a complete audit trail.

## Non-negotiables

1. **Host purge primitives only.** Destructive operations execute through host-sanctioned, manifest-driven, forbidden-tables-guarded primitives (landed in the host repo first; `requires_host_min_version` pins them). The cleaner orchestrates, previews, audits — it never free-roams with raw `DROP TABLE`.
2. **Fixed safety order:** dry-run plan → backup (when enabled) → quarantine/move → typed-confirmation destruction → audit log.
3. **Orphan candidates are never auto-dropped.** Always human-reviewed, individually or bulk-selected, behind a typed confirmation, with backup.
4. **Protected set:** host core tables (forbidden list), `first_party_module_keys` modules unless explicitly unlocked by the operator, and the cleaner itself (except via the dedicated self-destruct flow).

## Core features (from the Worksuite ModuleCleaner mining, adapted to the Longlink runtime)

- **C1 Residue inventory:** per-module view across installed/disabled/uninstalled modules (the host retains `addon_modules`/package records after uninstall — use them as the registry, not filesystem scans): owned tables (rows/size), settings values for module-declared keys, `<key>.*` permission rows, navigation rows, storage dirs (`storage/app/modules/<key>/`), stored package zips, profile documents.
- **C2 Orphan detection:** `information_schema` diff against (core tables + every known module's ownership manifest), prefix heuristics (`<key>_`, `addon_<key>_`), secondary migration-parsing discovery; ignore-list for host core prefixes; candidates listed with row counts and sizes.
- **C3 Removal plans:** dry-run preview of exactly what a "complete removal" or "residue purge" will touch; per-surface opt-in/out; "keep data" vs "purge data" choice.
- **C4 Backup sets:** SQL dump (schema + chunked inserts, FK checks wrapped) + files zip + manifest.json per removal; list/restore/retention purge.
- **C5 Quarantine:** move-don't-delete for files (rename-first, copy+delete fallback) under `storage/app/modules/module_cleaner/quarantine/`, with restore, purge, and retention cleanup.
- **C6 Dependency graph:** module-to-module dependency scan + reverse dependents; dependents block removal unless overridden.
- **C7 Audit log:** `module_cleaner_cleanup_logs` (module, version, action, status, tables_dropped, files_deleted, size_freed, backup ref, details JSON, actor, timestamps) + retention.
- **C8 Self-destruct:** the cleaner removes itself through the same host primitives, double-confirmed, always backed up.
- **C9 Operator UX:** dashboard, per-module residue page, orphans page, quarantine page, backups page, logs page; typed-confirmation gates ("CONFIRM DROP" / "PURGE" / "SELF DESTRUCT") re-validated server-side; super-admin-only permissions `module_cleaner.*`.

## Mining sources (operator's Worksuite modules — adapt, never paste; strip nwidart/company-context assumptions)

`ModuleScannerService` (registry + orphan detection + aggressive migration parsing), `UninstallService` (sequencing, uninstall-hook protocol, staged error collection, partial/failed statuses), `BackupService` (SQL dump strategy + zip + manifest + retention), `QuarantineService` (rename-first move), `DependencyGraphService` (namespace scan + reverse graph), `ModuleCleanupLog` (audit schema), the typed-confirmation view patterns (orphans/quarantine/self_destruct blades).

## Acceptance criteria

| # | Acceptance |
|---|---|
| CA1 | Module installs/enables through Addon Modules on a clean host; super-admin-gated UI appears |
| CA2 | Complete removal of a test module (generated by the Module Generator) leaves zero orphans: tables, settings, permissions, navigation, storage, packages all gone or explicitly retained by operator choice |
| CA3 | Orphan scan finds a deliberately planted orphan table and never auto-drops it; drop requires typed confirmation and produces a backup |
| CA4 | Backup set restores a removed module to working order |
| CA5 | Quarantined files restore intact; retention purges work |
| CA6 | A module with dependents cannot be removed without explicit override |
| CA7 | Every destructive action lands one audit row with full details JSON |
| CA8 | Forbidden/core tables are untouchable through every code path (regression-tested) |
| CA9 | Self-destruct removes the cleaner completely via host primitives, leaving only its backup set |
